Эта инструкция пережила три версии за сутки, и каждая прошлая версия содержала ошибку,
пойманную снаружи. Поэтому она устроена так: сначала СТАТУС (что уже сделано и не надо
делать снова), потом ГЕЙТ (обязательный чек-лист любой будущей подачи), потом ВОРКФЛОУ
(как подавать с минимумом ручных действий), потом ОТКРЫТЫЕ ПУНКТЫ и ИСТОРИЯ ОШИБОК.

## ГЕЙТ: обязательный чек-лист ЛЮБОЙ будущей подачи в OEIS

Ни одна подача не уходит, пока отдельный агент (не автор подачи) не проставил все пункты.
Каждый пункт — оплаченная боль: в скобках указано, чьим письмом он оплачен.

1. **Прайор-арт.** Проверить: (а) КОММЕНТАРИИ самой записи — оценки часто живут там, а не
   в DATA; (б) все ССЫЛКИ записи, включая финальные отчёты конкурсов (у AZsPCs очки могут
   кодировать значения — у Tetrahedra это квадраты размеров); (в) поиск OEIS по значениям
   и по хвостам; (г) литературу. Подавать ТОЛЬКО строгие улучшения. Ничьи и проигрыши —
   никогда. (Хаурой-д, A280537: «This isn't helpful to anyone».)
2. **Данные, а не проекты.** Свидетели — в плоском текстовом a-файле, приложенном к записи
   (стандарт ниже). Ссылка на GitHub — только вторичная, с текстом «Verification programs».
   (Хаурой-д, A399138: «no one in their right mind is going to hunt through your github
   repository».)
3. **Стиль комментариев.** Короткие фактические абзацы; в ЧУЖОЙ последовательности каждый
   абзац подписан «- _Aleksei Kudriashov_, Mon DD YYYY»; между абзацами ПУСТАЯ строка
   (иначе они склеятся в один %C); никаких рассказов о методе (метод — в Zenodo/ссылках);
   статус утверждения указывать (доказано / эмпирически); чужие конструкции атрибутировать
   точно (пример: случай Q = x^2 + y^2 — это конструкция Пора-Вуда, наша — только снятие
   условия p == 3 (mod 4)). (Хаурой-д: «most of the comments could be deleted».)
4. **Установленный член** идёт в DATA + строка в EXTENSIONS с источником, не в COMMENTS.
   Перед этим проверить b-файл: если в internal format нет %H-строки на bNNNNNN.txt —
   файл автогенерируется из DATA, загружать и синхронизировать нечего.
5. **Ловушки формы загрузки файла:** галка «This is a b-file (additional terms)» — ТОЛЬКО
   для настоящих b-файлов (для a-файлов снять); поле «Text for Link line» заполнить
   (заменить плейсхолдер TITLE FOR LINK); ссылку на файл руками в LINKS не дублировать —
   её создаёт виджет.
6. **ИИ не автор нигде** — ни в подписях, ни в текстах ссылок («Aleksei Kudriashov and
   Claude agents» в LINKS было ошибкой, исправлено). Ответственность — на авторе записи;
   быть готовым подтвердить чтение oeis.org/wiki/Use_of_AI_for_OEIS_Submissions
   (Пфёртнер спросил прямо — ответ дан 20.08, формулировка в истории A399138).
7. **Провенанс обязан совпадать с git-историей.** Хаурой-д за 30 секунд поймал в README

   неделе» по данным GitHub. Правило то же, что для статей: каждое утверждение о
   происхождении файла/числа проверяемо, или его нет. (TODO ниже.)
8. **Тон редакторов — не тема для ответа.** Отвечать починенным артефактом плюс одна строка

## ВОРКФЛОУ «internal format»: человек делает одну вставку

У редактора записи есть режим **«edit internal format»** — вся запись одним текстом в
%-строках вместо десятка полей. Целевой процесс любой будущей подачи:

1. Агенты готовят: (а) полный блоб internal format; (б) a-файл по стандарту ниже;
   (в) отчёт самопроверки: каждое число блоба перепроверено, таблица прайор-арта приложена,
   чек-лист гейта проставлен вторым агентом.
2. Человек: залогиниться → страница записи → edit → «edit internal format» → вставить блоб →
   Save → галка загрузки файла (пункт 5 гейта!) → приложить a-файл → propose.
3. Ответы редакторам: письмо пересылается в пайплайн, наружу уходит готовый блок для
   вставки. Человек не формулирует ничего сам.

## Стандарт a-файла (по образцу принятых a399138.txt, a280537.txt)

* Имя: `aNNNNNN.txt`. Только ASCII, только английский. Никаких русских комментариев
  (в certs/ они допустимы, в OEIS-файле — нет).
* Шапка: что это, определение задачи, координатная конвенция (0..n-1), метод проверки
  одной строкой, список сертифицируемых утверждений, имя и дата.
* Блоки: `n = K, M points (статус: optimal / best known, certifying a(K) >= M):`,
  затем точки `(x,y,z)` по десять на строку.
* Генератор обязан: записать файл, ПЕРЕЧИТАТЬ его с диска, распарсить обратно и повторно
  прогнать полную проверку (все тройки/четвёрки) уже по содержимому файла. В OEIS уходит
  только перечитанное.
