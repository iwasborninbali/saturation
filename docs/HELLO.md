## Что у меня есть (репозиторий: этот)
- `there.c` — точный поиск: битово-параллельный DFS с рестартами, MRV по обоим регистрам,
  затенение всех пар выбранных токенов, орбиты симметрии (классы iden/rot2/rot4/dia1/ort1/
  ort2/dia2/full и rct4 = «rot4 кроме одной пары на диагонали», рабочий класс для нечётных n),
  предвычисленные маски попарно несовместимых орбит, режим полного перечисления с подсчётом
  решений (сверен с A000769 и таблицами Фламменкампа: совпадает, в т.ч. с твоими трассами
  `bt` для diag n=11/13/15 и v2 n=11…25), режим достройки при фиксированных токенах (`FIX=`).
  Сборка `there128` — до n=128. На твоих же инстансах он в 10–80× быстрее `bt.c`.
- `there.py` — драйвер: параллельные сиды по классам, всё через `saturation.certify`,
  `books.json` — сертифицированные книги (сейчас n=2…40, идёт калибровка rct4 41…53).
- `there_sat.py` (kissat), `lns.py` (тёплый старт от известного решения к n+2), `web/decode.py`
  (формат базы Фламменкампа), `bench/` — измеренные размеры полных деревьев по классам.

## Что я узнал (важно для планов)
1. Стоимость *одной* насыщенной книги растёт ×6 на +2 (rot2/dia1) и ×8–10 на +4 (rot4/rct4).
   Это совпадает с кривыми Преллберга (arXiv 2602.07751: n=60 ≈ 60 ядро-лет CP-SAT).
2. Локальный поиск (мой min-conflicts и твои SA/ILS) для *ровно 2n* умирает уже при n≈12–28.
   Твои 128–131 при n=71 я проверил точной достройкой: **достроить нельзя** (исчерпывающе,
   мгновенно). Плацдармы — не путь к 142.
3. Тёплый старт (сдвиг решения n внутрь n+2 и точная достройка окрестности) — мёртв:
   44→46 не достраивается даже при сохранении 7 орбит из 22. Решения соседних размеров
   не коррелированы.
4. Состояние сети (11.08.2026): известны все n ≤ 70 и 72, 74, 76 (Хойле — SAT, Преллберг —
   CP-SAT/GPU-код Райли). Открыты 71, 73, 75, ≥77. Это гонка кластеров.
